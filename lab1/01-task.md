## 1. Постановка задачи для проектирования

### Продукт: **EduPath** — платформа управления обучением

### Социальная задача
Люди, которые хотят учиться самостоятельно или в рамках учебного заведения/компании, сталкиваются с разрозненностью инструментов: видео — на одной платформе, тесты — в почте или мессенджере, обсуждения — в чатах, дедлайны — нигде не фиксируются. Преподаватели тратят время на ручную проверку заданий и не видят общей картины прогресса группы. Задача — дать единую систему, где курс объединяет материалы (текст, видео), проверку знаний (тесты, письменные задания) и общение (форум), с разграничением ролей: гость может ознакомиться с каталогом, студент — учиться, преподаватель — вести курс, администратор — управлять платформой.

### Структура данных
Основные сущности: **Курс** (название, описание, категория, автор-преподаватель), **Пакет курсов** (объединяет несколько курсов, например «специализация»), **Модуль/Урок** (часть курса), **Материал** (видео или текст, принадлежит уроку), **Тест** (набор вопросов с автоматической проверкой), **Задание** (письменная работа с ручной проверкой преподавателем), **Отправленная работа** (ответ студента + оценка + комментарий), **Форум/Тема/Сообщение** (обсуждение в рамках курса), **Пользователь** (гость/студент/преподаватель/администратор), **Запись на курс** (студент + курс + прогресс), **Сертификат** (по итогам успешного прохождения курса).

### Структура деятельности
1. **Гость:** просмотр каталога курсов → просмотр описания курса (программа, автор, отзывы) → регистрация.
2. **Студент:** поиск/выбор курса → запись на курс → изучение материалов (видео/текст) по модулям → прохождение тестов → выполнение и отправка заданий → участие в форуме курса → отслеживание прогресса → получение сертификата по завершении.
3. **Преподаватель:** создание курса → наполнение модулей материалами → создание тестов и заданий → проверка присланных работ и выставление оценок → ответы на вопросы в форуме → просмотр статистики по студентам курса.
4. **Администратор:** модерация/публикация новых курсов → управление категориями каталога → управление пользователями (блокировка, смена роли) → просмотр отчётности по платформе в целом.

### Функциональность (базовая, по варианту задания)
- каталог курсов и пакетов курсов (специализаций);
- публикация текстовых и видео-материалов в составе курса;
- форумы для коммуникации в рамках курса;
- задания (письменные работы с ручной проверкой) и тесты (автоматическая проверка) для контроля знаний;
- доступ для ознакомления (гостевой просмотр каталога и описаний курсов без записи);
- ролевая модель: гость, студент, преподаватель, администратор.

### Расширение задачи на основе анализа конкурентов и опроса пользователей
По результатам анализа конкурентов (см. [02-competitors.md](02-competitors.md)) и опроса (см. [03-survey.md](03-survey.md), n=19) базовая функциональность дополнена и переприоритизирована:
- **мотивационные механики (прогресс, сертификат) — повышенный приоритет**: в опросе 58% назвали нехватку мотивации главной сложностью, 84% — главной причиной бросить курс, а «больше мотивационных механик» — один из двух лидеров по запросу на улучшение (37%, наравне с «больше практики и заданий»);
- отслеживание прогресса прохождения курса (шкала выполнения по модулям) — важно для 79% опрошенных;
- push/веб-уведомления о дедлайнах и новых материалах — хотят получать 84% опрошенных;
- сертификат по итогам курса при выполнении критерия завершённости — важен для 68%;
- оценки/отзывы курсов от студентов для помощи в выборе (как у Stepik, Coursera);
- фильтрация и поиск курсов по категории, уровню сложности, длительности;
- офлайн-доступ к скачанным материалам в мобильном приложении сохранён как второстепенная функция (спрос умеренный: 42% опрошенных пользуются офлайн-режимом хотя бы иногда, 58% — не пользуются).

Видеолекции при этом оказались лишь на 5 месте по важности из 8 функций (53%), уступая тестам (89%), прогрессу (79%), текстовым материалам (74%) и сертификату (68%) — на старте прототипа приоритет отдан тестам и трекингу прогресса, а не видео-контенту.

## 2. Требования к физической инфраструктуре прототипа мобильного устройства

По данным опроса 95% студентов учатся с компьютера/ноутбука и только 5% — со смартфона, преимущественно дома (84%). Мобильное приложение в этом продукте выступает **компаньоном веб-платформы** (уведомления, быстрый просмотр прогресса, чтение текстовых материалов, повторение перед тестом), а не основной площадкой для видео и тестов — этому подчинены его сценарии ниже.

**Форм-фактор:** смартфон, портретная ориентация как основная (короткие сессии — проверить прогресс, прочитать уведомление, повторить конспект); полноценное прохождение теста/видео остаётся на вебе.

**Способы управления:**
- сенсорный ввод (тап, свайп между карточками курсов и уведомлениями);
- клавиатура устройства — для коротких действий (быстрый ответ в форуме, короткий тест на повторение), не для основного прохождения курса;
- push-уведомления как основной канал ценности мобильного приложения (напоминания о дедлайнах, новые материалы, ответы на форуме) — приоритетная функция по данным опроса (84% хотят уведомления);
- голосовые подсказки/субтитры к видео — опционально для доступности, если видео всё же открывается в приложении.

**Ограничения контекста использования:** приложение должно поддерживать скачивание текстовых материалов для чтения без интернета как дополнительную, а не ключевую функцию (спрос умеренный — см. выше); прогресс прохождения должен синхронизироваться между вебом и мобильным приложением без потери данных о пройденных тестах.
